### 2026-08-18 — Fix "Iframe Sandbox Detected" for users whose first source fails
- **Changed:** `apps/web/src/pages/MoviePage.jsx` + `TVPage.jsx` — both player iframes now carry `key={playerSource}`, so a source switch builds a fresh iframe instead of renavigating the existing one (see Decided). `apps/web/src/ipc/polyfill.js` — `openPipWindow` was a no-op stub on web, which left the pop-out button dead and the user with no way out of a broken embed; it now opens the provider URL in a new tab (called from a click handler, so popup blockers allow it). `apps/web/public/sw.js` — cache bumped to `movievault-shell-v2` (the `activate` purge only runs when the name changes) and non-`/assets/` same-origin responses moved from cache-first-forever to stale-while-revalidate; hashed build assets stay cache-first because their URLs already change per deploy. `apps/web/src/main.jsx` — registration now calls `registration.update()` and reloads once when a *replacement* worker takes control, so a client can't sit on an old build for the life of a tab or installed PWA.
- **Decided:** ADR-017 — the player iframe is remounted on every source switch. Diagnosis: the deployed bundle provably emits **no** `sandbox` attribute for Videasy (grepped the live `index-*.js`), yet a user's friend saw Videasy's "Iframe Sandbox Detected" page with the source chip reading "Videasy". The reachable explanation is an in-place sandboxed→unsandboxed switch on a reused iframe, where the old sandbox flags survive the navigation. Every path into it (`PlayerTroubleBar`'s wrap-around "Try another source", the manual picker, the Phase 3 reachability auto-switch) only fires for users whose first source fails — which is exactly why it reproduced for one person and not the other on the same build. Reasoning and the rejected alternative (relying on React's prop-application order) are in ADR-017.
- **Deviations:** The session started as a question, not a plan, so no new plan doc was written — this is a bug fix against behaviour already specified in ADR-013/ADR-016 and `PLAN_WEB_ADDRESSABLE_UX.md`. The service-worker and pop-out changes are defensive: they were not proven to be the cause, but each independently keeps a broken embed recoverable, and the SW versioning closes the "stale build pinned to one client" path that would otherwise mask the fix.
- **Known issues / next steps:** Not verified against the friend's actual environment — confirmation is that switching to Videasy from a sandboxed source no longer shows the provider's sandbox page. The smoke suite is 3/4: `first-run flow, home shell, and search modal are usable` fails on the search-modal step because a concurrent in-progress refactor in the working tree replaced `SearchModal.jsx` with `SearchPage.jsx` (the `Search movies and series...` placeholder no longer exists anywhere in `src/`); unrelated to this fix, and the test needs updating with that refactor. Lint counts are unchanged from HEAD on all touched files. Changes are uncommitted and undeployed, and the working tree also holds that unrelated concurrent work — stage selectively.

### 2026-07-08 — Pop-up Shield (source-preference ad mitigation) + native-player plan
- **Changed:**
  - `apps/web/src/utils/api.js` — added `sourceIsProtected(sourceId)` (`sourceSandbox(id) !== null`); tagged Videasy `note: "pop-up ads"` so the source picker shows the trade-off.
  - `apps/web/src/utils/sourceQueue.js` — added `getPopupShield`/`savePopupShield` (persists `popupShield`, default off, dispatches a `movievault:popup-shield-changed` event); `getQueue` now stable-partitions protected sources ahead of unprotected ones when the shield is on, otherwise keeps the existing videasy-first order.
  - `apps/web/src/pages/SettingsPage.jsx` — "Pop-up Shield" checkbox in the Video Sources & Failover section explaining the trade-off (prefer VidSrc/2Embed which allow browser popup-blocking; Videasy becomes last-resort).
  - New `refdocs/plans/PLAN_NATIVE_PLAYER.md` + `refdocs/execution/EXEC_NATIVE_PLAYER.md` — plan for the *real* fix (client-side stream extraction → own `<video>` player, P-Stream architecture), gated on a Phase 0 provider-success-rate spike. README tables + `refdocs/changelog/DECISIONS.md` ADR-016 added.
- **Decided:** Embed pop-up ads (Videasy opening a tab on play/pause) **cannot** be blocked from the parent page — an unsandboxed cross-origin iframe can `window.open()` on any gesture and there's no parent API to stop it, and Videasy refuses to run sandboxed at all (ADR-013), so there's no config where we both play Videasy and block its popups. Two levers only: prefer sandbox-accepting sources (this shield), or stop embedding and extract raw streams (the native-player plan). Shield is off by default because Videasy is the most reliable source; enabling it only reprioritizes and never removes Videasy from the failover chain (still falls through to it last). Full reasoning in ADR-016.
- **Deviations:** None — additive feature + planning docs.
- **Known issues / next steps:** Shield is a mitigation, not a cure — protected sources have smaller catalogs (2Embed is already `unstable`), so shield-on users may hit "all sources failed" on some titles. The native player (`PLAN_NATIVE_PLAYER.md`) is the actual ad-free path; its Phase 0 spike (measure `@p-stream/providers` / cinepro-core extraction success on ~20 titles) is the go/no-go gate before any of it is built. Queue ordering verified with a 5-case unit test; the shield was **not** live-tested in a browser this session (safe regardless — it only reorders an existing, fallback-protected queue).

### 2026-07-08 — Hotfix: sourceSandbox null-coalescing bug (Videasy sandbox fix never worked) + trailer modal broken by go-away anti-bot
- **Changed:**
  - `apps/web/src/utils/api.js` — `sourceSandbox()` rewritten: the previous `?.sandbox ?? DEFAULT_SANDBOX` coalesced Videasy's **explicit `sandbox: null`** back into the default sandbox string (`??` fires on null as well as undefined), so the entire ADR-013 fix shipped in `f71c8f5` never actually took effect — the deployed site still showed "Iframe Sandbox Detected" on Videasy. Now `null` passes through (JSX `|| undefined` then omits the attribute) and only unknown sources / missing fields fall back to the default. **Verified with a real unit test this time**: bundled the actual `api.js` via esbuild and asserted all 6 cases (videasy→null, videasy`||undefined`→undefined, vidsrc/2embed/allmanga→default string, unknown→default string) — all pass.
  - `apps/web/src/components/TrailerModal.jsx` — full rewrite for the browser. The old component was Electron-webview code: it walked 9 Invidious instances relying on `did-finish-load`/`did-fail-load`/`executeJavaScript` (never fire / don't exist on a browser `<iframe>`), so on web the loading overlay never cleared and no failover ever ran; separately the default instance (`inv.nadeko.net`) now serves a "go-away" anti-bot Forbidden page. Web now embeds `youtube-nocookie.com` directly (consistent with ADR-007 — HeroBanner already uses a YouTube iframe), honors a user-set custom Invidious instance from Settings (only when it differs from the default, since SettingsPage persists the default value on save), clears the spinner via a real `onLoad`, and "Open in Browser" opens the matching watch URL with a `window.open` fallback. `DEFAULT_INVIDIOUS_BASE`/`getInvidiousBase` exports kept (SettingsPage imports them).
  - `src/components/TrailerModal.jsx` (Electron) — the bot-page detector's keyword list didn't recognize the go-away block page ("Oh no! Forbidden … denied by administrative rule … Protected by go-away"), so the desktop app displayed the block page as if it were the trailer instead of failing over to the next instance. Added `forbidden`, `access denied`, `denied by administrative rule`, `go-away`, `anubis`, `rate limit` to the keywords — Electron's instance-failover chain now skips these pages.
- **Decided:** On web, blind Invidious failover is unfixable in principle: a cross-origin iframe's block page fires `onLoad` exactly like a working player and its content can't be inspected, so there is no signal to fail over on. YouTube's own embed is the only reliably embeddable trailer source in a browser — hence the split: Electron keeps the Invidious probe-and-failover (it has `executeJavaScript`), web uses YouTube directly.
- **Deviations:** None planned — this is a regression-fix session driven by two user-reported production screenshots.
- **Known issues / next steps:** Re-verify both fixes on the live Vercel deploy after this push (Videasy plays without the sandbox page; trailer modal plays). The Electron keyword fix is on `main` (V2 app); mirror it to `redesignuiux` when that branch is next touched.

### 2026-06-17 — Fix serverless functions crashing (ESM vs CommonJS) — proxy + AllManga
- **Changed:** Converted `apps/web/api/proxy.js` and `apps/web/api/resolve-allmanga.js` from CommonJS (`require`/`module.exports`) to ESM (`import`/`export default`).
- **Decided:** Verified against the live deployment that BOTH serverless functions returned 500 `FUNCTION_INVOCATION_FAILED` with runtime log `ReferenceError: require is not defined`. Fixes both the One Pace Pixeldrain proxy and AllManga (anime) resolution — AllManga playback on web was broken by the same root cause.
